## Context

当前工作区仅有参考项目 `deepseek-harness/`（用于对齐前端客户端模块架构与界面结构），**平台本身尚无任何实现**。约束来自需求本身：约 100 个席位、配置驱动扩席位不改代码、多方案与多仿真必须并发、仿真系统可插拔（MCP）、每项能力需可执行断言。动机见 `proposal.md - Why`，行为要求见 `specs/` 下各能力规格。

## Goals / Non-Goals

**Goals:**

- 在单一进程内运行约 100 个彼此隔离的席位运行时，并让并发任务的总耗时接近最慢单席
- 组织模型、技能编排、仿真接入全部配置驱动，扩席位／换仿真不改代码
- 知识库检索前完成权限过滤，杜绝命中即泄漏
- 仿真系统经 MCP 热插拔，单系统失败不影响整体
- 产出默认挂起待审，形成人在回路闭环
- 前端控制台承载 `specs/web-console` 中的 11 个功能模块
- 每项能力配套可复跑的断言测试

**Non-Goals:**

- 前端视觉与交互设计（配色、布局、组件规范、动画、响应式）
- LLM 模型训练与微调；具体 LLM Provider 的选型（见 Open Questions）
- 生产级分布式部署（K8s、多租户、水平扩容）
- 用分布式组件替换知识库与消息总线——仅预留接口
- 任何具体军事战术、武器操作或涉密内容（Skill 仅含公开方法论与流程框架）

## Decisions

### 1. 技术栈：TypeScript + Node.js（后端）与 React + Vite（前端），断言用 Vitest

与参考项目 `deepseek-harness` 保持同构，便于对齐前端客户端模块结构；MCP 官方提供 TypeScript SDK；前后端同语言降低心智与构建成本。

- 备选：Python —— AI 生态更好，但与前端割裂，且难以对齐 `deepseek-harness` 的 TS 客户端架构。

### 2. 席位隔离：进程内逻辑隔离，而非 OS 级隔离

每个席位持有一个独立的运行时上下文（独立人格、三层记忆、技能视图、会话与权限边界），互不共享可变状态。

- 理由：100 个独立进程／容器在资源与运维上不可行；"总耗时≈最慢单席"靠进程内并发即可达成，隔离需求通过上下文边界满足。
- 备选：每席位一个进程 —— 隔离更强，但资源与运维成本过高，且与 hermes-agent 单实例设计被排除的原因相同。
- 补充：这也是**不直接引入** `hermes-agent` 的原因——其单实例设计无法在同一进程内跑 100 个隔离席位，仅对齐其自进化闭环与三层记忆的设计思路。

### 3. 并发调度：统一并发执行器，基于 `Promise.all` / `Promise.allSettled` 并支持可配并发上限

多方案生成与多仿真推演均走同一执行器。

- 理由：`Promise.all` 满足"总耗时≈最慢单席"；`allSettled` 天然满足"单个仿真系统失败不中断整体"。并发上限用于防止下游限流。
- 备选：串行（直接违反并发要求）；Worker 线程池（复杂度高，当前规模无收益）。

### 4. 配置模型：YAML + 启动时 schema 校验

`config/seats.yaml`（席位与角色、指挥链 `parent`、活动与阶段）、`config/skills.yaml`（启用、角色授权、技能包）、`config/simulators.yaml`（MCP 启动命令、工具名、权重）。启动时加载并校验，失败即中止并给出明确错误。

- 理由：需求明确指定这些路径并要求"加条目即可"；schema 校验避免配置错误静默生效。
- 备选：JSON（不支持注释，对业务人员不友好）；代码定义（违反配置驱动）。

### 5. 人格外置：按 席位级 > 角色级 > 内置默认 依次回退查找 Markdown 文件

业务人员改 Markdown 即可调整人格，无需改动代码。

### 6. 知识库权限：检索前先算可见集，再在可见集内检索

先按 `deny`（优先）与 `allow` 及角色密级算出可见文档集合，检索仅在可见集内执行；不可见文档不进入候选集，也不出现在匹配计数、摘要或片段等任何返回字段中。

- 理由：避免"命中即泄漏"。
- 备选：先检索再过滤 —— 已被需求明确禁止。

### 7. Skill 装配：有效技能 = 引用 ∩ 授权 ∩ 启用

技能可用需同时满足：角色通过 `packs`/`skill_allow` 引用、注册表 `allowed_roles` 允许、`enabled` 为 true。管理员编排配置覆盖 SKILL.md 内嵌 `metadata`。

### 8. 仿真接入：MCP stdio 客户端 + 权重归一化加权

按配置 spawn 子进程（command/args），调用指定 tool，传入 `{plan_id, plan_name, plan_content}`，解析 `{score, metrics, narrative, success}`；连接或调用失败仅标记未连接。加权仅对成功的系统做权重归一化：`sum(score_i × w_i) / sum(w_i)`。

- 理由：权重和为 1 时即为加权求和（符合规格场景 0.7×80 + 0.3×60 = 74）；部分系统失败时归一化避免整体得分被低估。
- 备选：算术平均（忽略权重，违反需求）。

### 9. 自进化产物：独立目录 + 强制低密级 + 留痕回滚

产物写入 `runtime/` 下独立目录（与手写 `skills/` 隔离、不污染版本控制），强制 `clearance=1`，危险指令命中即拒绝固化，变更写入日志并保留前镜像以支持回滚。

- 备选：直接写入 `skills/` —— 污染手写技能库与版本控制，违反需求。

### 10. 消息总线：先定义接口，初期进程内内存实现

群聊、直达、`@` 提及、指挥链广播、会话分支均通过统一 `MessageBus` 接口。

- 理由：当前规模无需分布式；接口抽象便于后续替换为 Redis Streams / Kafka。
- 备选：直接引入 Kafka —— 过度设计。

### 11. 记忆持久化：每席位三层记忆序列化到 `runtime/memory/<seat-id>/`

提供 `persist()` 与 `restore()`，使集群重建后记忆可召回。

- 备选：SQLite —— 更重，当前不需要复杂查询能力。

### 12. 前端：按功能模块组织，仅对齐结构不做视觉

使用 React + Vite + TypeScript，按 `specs/web-console` 的 11 个功能模块划分，客户端模块结构对齐 `deepseek-harness`；数据经本地 API 层获取，视觉与交互设计不在本次范围。

## Risks / Trade-offs

- **[100 席位并发触发 LLM 限流与成本]** → 引入可配并发上限与排队；测试阶段使用 mock provider 保证断言可复跑。
- **[进程内逻辑隔离不足以防止记忆串扰]** → 运行时上下文强制隔离，并以"席位间运行时互不干扰"断言测试防回归。
- **[MCP 子进程泄漏或僵尸进程]** → 统一 spawn 管理、调用超时与 dispose 清理，进程退出时回收子进程。
- **[配置错误静默生效]** → 启动时 schema 校验，失败即中止并给出明确错误位置。
- **[知识库权限过滤随文档量增长成为瓶颈]** → 初期文档级过滤可接受；生产阶段替换为 RAGFlow / WeKnora（内置 RBAC）。
- **[自进化产生低质或危险规程]** → 强制低密级 + 危险指令黑名单 + 人工审核，产物不自动生效。
- **[前端本次仅功能骨架]** → 明确不含视觉；结构对齐 `deepseek-harness` 以便后续套用视觉规范。

## Migration Plan

按阶段推进，每阶段配套可执行断言（顺序与细节见 `tasks.md`）：

1. 工程骨架与配置加载（含 schema 校验）
2. 席位／角色／指挥链／活动模型
3. Agent 运行时（人格、三层记忆、隔离）
4. 知识库与检索前权限过滤
5. Skill 体系与 zip 上传安全
6. 协同消息与任务审批闭环
7. MCP 仿真接入与加权择优
8. 自进化闭环
9. 前端控制台模块

回滚：各阶段独立提交；配置与 `runtime/` 产物目录可清空重建；自进化产物支持单独回滚到变更前状态。
